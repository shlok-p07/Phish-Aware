# PhishAware

**A gamified phishing-awareness platform that trains employees against
AI-generated, role-specific attack scenarios — and proves the training
worked with real analytics.**

Most security-awareness training is a slideshow once a year. PhishAware drops
people into a realistic, fully simulated inbox, has them judge whether a
message is phishing, flag the specific cues that gave it away, and rate their
own confidence — then scores the attempt instantly. Every scenario is
disposable and synthetic: nothing you interact with is a real email, a real
link, or a real credential prompt.

## Why it's interesting

- **The scenarios are LLM-generated, not templated.** A two-stage pipeline
  drafts each attack for the employee's actual role and department, then
  refines it for realism and grounds every red flag in the app's own
  gradeable cue vocabulary. See
  [`src/server/scenarioGenerator.ts`](src/server/scenarioGenerator.ts).
- **It's built to survive a real free-tier LLM outage.** Every model call goes
  through a Groq-primary, Gemini-fallback layer
  ([`src/server/llm/llmComplete.ts`](src/server/llm/llmComplete.ts)) so a
  provider hiccup degrades gracefully instead of breaking training or the
  in-app assistant.
- **Enterprise SSO is a real, from-scratch OIDC implementation** —
  authorization code + PKCE (S256), single-use state, nonce binding, full
  ID-token validation against a cached JWKS — not a third-party auth SDK. See
  [Single sign-on](#single-sign-on-oidc).
- **The database schema is enforced, not just assumed.** MongoDB's
  `$jsonSchema` validators are the actual source of truth for every
  collection (`phishaware-db/init/`), and the app provisions and seeds itself
  idempotently on boot — a fresh teammate or a fresh deploy needs zero manual
  setup steps.
- **The API is generated, end-to-end, from one spec.** Request/response types,
  Zod validation, and every React Query hook are generated by
  [orval](https://orval.dev/) from a single OpenAPI document
  (`src/api-spec/openapi.yaml`), so the client and server can't silently drift
  apart.
- **540 tests, `tsc --noEmit`, and a production build all stay green.**

## Features

- **AI-generated phishing scenarios**, matched to the employee's department
  and role, with difficulty that adapts to their accuracy over time.
- **PhishAware Assistant** — an in-app chatbot (Groq/Gemini) that explains
  cues and answers phishing questions in plain language, no markdown noise.
- **Realistic practice across three vectors** — a Gmail-style inbox, an SMS
  thread, and a simulated phone call with a live, speech-synced transcript.
  Flag red flags, set a confidence level, get graded, cue-by-cue feedback.
- **Lessons spanning six attack vectors** — email, SMS (smishing), voice
  (vishing), QR codes (quishing), social media, and fake websites.
- **Personal & org analytics** — accuracy over time, per-cue and per-vector
  breakdowns, and a calibration score measuring how well confidence tracks
  actual correctness.
- **Gamification** — XP, levels, daily streaks, badges, and a team
  leaderboard, so recurring training is something people return to.
- **Adaptive onboarding** — a short diagnostic quiz sets each person's
  starting difficulty and department context.
- **Guest mode** — try the full product with zero commitment; progress
  carries over on signup.
- **Organization admin** — create an org, invite teammates, assign training
  campaigns, and see org-wide accuracy/risk analytics.
- **Single sign-on** — organizations can link Okta, Entra ID, Google
  Workspace, Auth0, or any generic OIDC provider. Membership stays
  invite-only regardless.
- **First-class accessibility** — text scaling, reduced motion, high
  contrast, a dyslexia-friendly font, and larger tap targets.

## Architecture

```
src/
├── app/                # Next.js App Router
│   ├── (app)/          # Authenticated app (dashboard, learn, practice, admin, ...)
│   ├── api/            # Route handlers (auth, lessons, practice, profile, org, ...)
│   ├── auth/           # Login / signup / SSO entry point
│   ├── invite/[token]/ # Public invitation accept page
│   ├── onboarding/     # Diagnostic quiz
│   └── page.tsx        # Public marketing landing page
├── api-spec/           # OpenAPI spec (openapi.yaml) + orval codegen config
├── api-client/         # Generated React Query hooks + fetch client
├── api-zod/            # Generated Zod request/response schemas
├── components/         # UI components (incl. shadcn/ui in components/ui)
├── db/                 # MongoDB client + collection models
└── server/             # Domain logic: grading, leveling, streaks, sessions, seeds
    ├── llm/             # Groq/Gemini completion layer, scenario generation, chatbot
    └── sso/             # OIDC: PKCE, discovery/JWKS cache, ID-token claims,
                          # decideSsoProvisioning() (the pure "who gets in" rule)

phishaware-db/init/     # $jsonSchema validators + indexes -- source of truth
                           for the Mongo schema

backend/                # Separate FastAPI service for ML model/dataset work
                           (see "ML backend" below) -- its own deploy, its own
                           dependencies, not part of the Next.js app
```

## Getting started

### Prerequisites

- [Bun](https://bun.sh/) `>= 1.3`
- A MongoDB connection string (e.g. [MongoDB Atlas](https://www.mongodb.com/atlas)'s free tier)

### Setup

```bash
# 1. Install dependencies
bun install

# 2. Configure environment
cp .env.example .env
# then edit .env and point MONGODB_URI at your MongoDB instance,
# and add GROQ_API_KEY / GEMINI_API_KEY for AI scenario generation + the assistant

# 3. Start the dev server
bun run dev
```

The app runs at [http://localhost:3000](http://localhost:3000). On first
request to any API route, the app provisions its own MongoDB schema
(collections, `$jsonSchema` validators, indexes) and seeds lessons/practice
scenarios/sample users if the database is empty — idempotent, and safe to run
against an already-provisioned cluster every time the server starts. No
manual setup script required for a fresh clone, teammate, or deploy.

docker compose up -d --build

Builds the app from the same `Dockerfile` used for deploys, against whatever
`MONGODB_URI` is in `.env`. Mainly useful for testing the production
container locally before deploying — day-to-day development doesn't need

</details>

## Admin / organizations

Signed-up users start without an organization. Creating one (`/admin/create`)
makes you its admin; from there you can invite members, assign training
campaigns, and view org-wide accuracy/risk analytics under `/admin`.

Inviting someone creates a token-based invitation (14-day expiry, no email
required) — the admin UI hands back a copyable invite link. Opening
`/invite/<token>` lets the invitee set a password or, if the org has SSO,
sign in with their company account. Seat limits are enforced at invite and
accept time.

### Single sign-on (OIDC)

Each organization can link its own identity provider — Okta, Microsoft Entra
ID, Google Workspace, Auth0, or any generic OIDC provider — under
**Admin → Organization → Single sign-on**. Access stays **invite-only**:
authenticating with the IdP is never sufficient on its own, the callback only
admits an existing member or pending invitation.

The flow is authorization code + PKCE (S256), with single-use `state` stored
in Mongo, nonce binding, and full ID-token validation (signature via cached
JWKS, `iss`, `aud`/`azp`, expiry) via `openid-client`. Client secrets are
encrypted at rest with AES-256-GCM under `APP_ENCRYPTION_KEY`. Without that
key, the app runs normally and SSO simply reports itself as unavailable.

<details>
<summary><strong>Setting up a connection</strong></summary>

1. In your IdP, create a web application and paste in the **redirect URI**
   shown on the settings card (`<your-origin>/api/auth/sso/callback`),
   exactly.
2. Enter the issuer URL, client ID, and client secret. The issuer has to
   match what the provider publishes character for character — Auth0's
   includes a trailing slash, and Entra's multi-tenant `common` issuer (a
   literal `{tenantid}`) is rejected because it can never be validated.
3. Add the email domains allowed to use this connection.
4. Hit **Test connection** — six server-side checks cover discovery, issuer
   match, endpoints, PKCE S256 support, JWKS, and whether the client
   credentials are valid. **Test sign-in** does a real round trip without
   creating a session.
5. Enable it.

Note on `email_verified`: Microsoft Entra never sends this claim. An
**absent** claim is treated as verified only when the address falls inside a
domain the admin explicitly allowlisted for that connection. An explicit
`false` is always rejected.

</details>

<details>
<summary><strong>Testing SSO end-to-end with Auth0's free tier</strong></summary>

1. **Applications → Create Application** → name it `PhishAware` → pick
   **Regular Web Applications** → Create.
2. In **Settings**, set **Allowed Callback URLs** to
   `http://localhost:3000/api/auth/sso/callback` and **Allowed Logout URLs**
   to `http://localhost:3000/auth` — exactly those, no trailing slash, no
   query string.
3. Copy **Domain**, **Client ID**, and **Client Secret** from Settings.
4. **User Management → Users → Create User**: `alice@acme.test`, any
   password, connection `Username-Password-Authentication`, then toggle
   **Email verified** on.
5. Put the values in `.env` (the issuer is the domain wrapped in `https://`
   **with a trailing slash** — the single most common setup mistake, which
   the preflight check exists to catch):

   ```bash
   SSO_TEST_ISSUER="https://dev-xxxxxxxx.us.auth0.com/"
   SSO_TEST_CLIENT_ID="..."
   SSO_TEST_CLIENT_SECRET="..."
   SSO_TEST_PROVIDER="auth0"
   SSO_TEST_EMPLOYEE="alice@acme.test"
   ```

6. With `bun run dev` running: `bun run sso:demo` — creates a demo org and
   admin, saves the connection, runs the six preflight checks against your
   real tenant, enables SSO only if they pass, issues an invitation for the
   test user, and prints the sign-in URL. Add `-- --reset` to tear it down.
7. Open `/auth`, click **Sign in with your company account**, enter
   `alice@acme.test`, and authenticate.

Worth trying afterward:

| Try this | Expected |
| --- | --- |
| An `@acme.test` address with no invitation | `not_a_member` |
| An address at any other domain | `domain_not_allowed` |
| Re-opening the completed callback URL | `invalid_state` (single-use) |
| Deleting the `phishaware_sso_state` cookie mid-flow | `invalid_state` |
| Setting the member's `status` to `disabled` in Mongo | `account_disabled` |

**Google Workspace instead:** issuer is `https://accounts.google.com` (no
trailing slash) and `SSO_TEST_PROVIDER="google"`. Google's issuer is shared
by every Google account, so the `hd` (hosted-domain) claim is what scopes it
to your org — you need a real Workspace domain, not a personal Gmail.

</details>

### Password reset

Forgot-password issues a 6-digit code, hashed with the same scrypt hash/verify
as account passwords, never stored or logged in plain text. The app has no
mailer, so the code comes back directly in the API response and is shown
on-screen (`src/components/forgot-password-dialog.tsx`) rather than emailed.

## ML backend (FastAPI)

`backend/` is a separate Python service, scaffolded MVC-style, for
phishing-related model/dataset work. It's not part of the Next.js app — its
own deploy, its own dependencies. Two endpoints, two different states:
message classification (is this specific message phishing?) is still a
placeholder heuristic (`backend/app/models/predictor.py`), ready to swap in
a trained model without touching the routing or API layer around it.
User-awareness prediction (how likely is this person to fall for phishing,
based on their onboarding survey/quiz answers) already runs a real trained
model (`src/server/mlClient.ts` calls it from
`src/app/api/onboarding/submit/route.ts`); if the service is unavailable,
onboarding falls back to diagnostic quiz accuracy instead.

## Safety

PhishAware is a training tool. Every scenario is simulated. The app never
asks for real passwords, payment details, or account access, and none of the
links or senders shown are real.
